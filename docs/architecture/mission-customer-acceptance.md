# 客户答复语义审查（独立于执行 Agent）

给定商机任务的自由文本验收条件、已核实发送回执与之后的 CRM 客户入站文本，负责人要判断客户是否明确接受了报价和交期；有用的结果是附原始消息 ID 与精确引文的支持、反对、含糊或证据不足，而不是 Agent 自称“已成交”。

`POST /api/v1/ai/missions/:id/customer-acceptance` 是显式、有模型费用的经理操作。服务端先按组织读取 Mission、商机与 Run，核对执行提案、批准正文哈希、发送账本与 CRM 出站消息，再只读同组织、同联系人、同会话、同渠道 session、具外部消息 ID 且发送后的客户入站文本。超过 20 条或单条 2000 字符时失败关闭，不把截断上下文交给模型。不存在已核实发送或入站时直接返回证据不足，不调用模型。

Judge 使用 CRM Model Gateway 与原 Run 版本的模型绑定；Pi 仍只负责模型循环。唯一可用的工具是内存中的 `submit_customer_acceptance_assessment`，没有 CRM 写入或外发端口。输出经 Zod 校验，并逐条要求 `messageId` 属于允许的入站材料、`quote` 是该消息原文连续子串。支持性判定必须有接受性引文且无缺失条款、反对或附条件引文。输入中的验收条件和客户正文均视为不可信数据，不执行其中指令。API 与 UI 只向经理返回判定、简要理由、消息 ID 与引文，不写入 Run 事件或审计事件。

模型即使给出 `supported`，`businessOutcomeVerified` 也固定为 `false`：引文只能证明 CRM 中有这段客户文本，不能证明客户身份、法律上的承诺或语义解读一定正确。负责人须结合原始会话复核。评审分支新增了独立的[明确报价与交期确认协议](mission-explicit-offer.md)：负责人先固定结构化条款，原样审批发送后，客户通过同渠道回复一次性确认语句。它可确定性核验这两个规范化字段的渠道回复，但尚未在真实客户渠道联调，也不能自动验收任意自由文本条款或证明法律身份。当前语义审查路径仍存在可解释冲突处理、避免重复模型费用的持久化缓存和完整端到端 UI 验收等限制。
