# Chat-first 演示与真实 API 路径：交付边界

日期：2026-10-01。此文对应本分支的生产代码增量；`examples/chat-first-demo/` 仍是独立的无 Key 实验室，不是部署后的 CRM，也不会被导入生产运行时。

## 功能矩阵

| 能力              | 真实实现与本次接线                                                                                                          | 明确边界                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 聊天式 Workbench  | 既有真实 API、Pi 模型循环、历史、SSE 重放、审批和停止；本分支保留聊天工作区                                                 | 每次发送仍是独立 Run；页面多轮展示不等于自动共享任意历史上下文；manager 角色要求不变                                                       |
| Wiki / RAG        | 既有真实 embedding + pgvector 检索；现在保留实际 chunk 的索引版本、位置、哈希和精确本地 URI                                 | 需另行就绪的 embedding 凭据、来源索引和 Agent 来源集合；不是仅填聊天 API Key 就全部就绪                                                    |
| 可读证据          | Run 详情从成功知识工具观察提取片段，重新核对当前 Agent 来源权限、组织、来源启用状态；旧索引显示需重查                       | 只返回允许的知识投影；不会提供全部工具 JSON、客户消息或模型内部状态；归档/撤权来源不再展示历史摘录                                         |
| 多 Agent 核查     | 既有持久子 Run、只读专家、父 Agent 单写者；保留嵌套知识 locator，修复同一 Wiki 不同段落被误报冲突                           | 同源不同索引仍报告 stale_state；不把摘录不同当成已确认业务矛盾；Mission 并发仍为 1                                                         |
| 组织版本记忆      | 共用 canonical resolver；inbound、Workbench 初始、批准后恢复和专家读取同一母文档 + active entries；记录快照 hash / 文档版本 | 恢复会重新读取当前发布版本并记录新 revision；不是冻结旧政策。hash 是来源指纹，不是新的发布 CAS 协议                                        |
| 客户记忆          | `crm_get_conversation_history` 现在附带当前会话服务边界内的只读持久 checkpoint，含 seq、时间、承诺、异议与下一步            | 按组织/联系人/会话/service revision/demanda 限定并重查边界与联系人可用性（匿名化/合并/删除即拒绝）；无当前范围则 unavailable/empty，不回退到其他会话；没有新增任意客户记忆写入/CAS |
| 持久任务          | 既有数据库队列、租约、重启恢复、审批后续跑、失败可见和不确定副作用核对；复用其真实实现                                      | 实验室的整条流程 pause/resume 按钮不等同生产通用 Run 暂停。生产保留取消 Run、等待审批和耐久恢复                                            |
| 暂停/恢复客户发送 | UI 接入既有 Mission 事务命令；填写原因，幂等 request key，失败可重试，返回后更新状态                                        | 只控制该 Mission 客户发送；调查可继续；在途消息不能保证撤回；恢复不会复活旧审批，须重新核对                                                |
| 跟进审批          | 既有真实跟进工具与审批执行；现在审批卡显示目标 ID 和绝对时间/执行批准后的相对小时数                                         | 不公开任意工具参数/客户正文；不确定已写入结果必须核对，不能按实验室脚本盲目重放                                                            |
| Eval / Trace      | 既有七项确定性评测读取真实 Run/工具/审批/子 Run；现在显示每项 finding 原因与代码、保留事件时间线                            | 读取评测材料失败/子状态损坏时拒绝评分；确定性检查不是事实自然语言语义或客户业务结果验收；语义 Judge 显式触发并消耗模型额度                 |
| 演示专有设计      | 浏览器 checkpoint、旧价/新价业务有效期规则、任意客户记忆 CAS、注入一次错误、完整本地 JSON trace 下载                        | 没有把这些 fixture 规则伪装成生产服务；生产索引版本不代表政策批准、生效日期或报价授权                                                      |

## 操作人员准备步骤

1. 按仓库现有 self-host 安装/更新流程应用当前 baseline，确认应用、数据库、事件 drainer/cron 和 Agent worker 正常运行。本次无 schema migration，不改工作流或保护规则。
2. 在 `/app/ai/credentials` 或 `/app/ai/providers` 配置组织自己的凭据和默认模型。选择目录声明支持工具调用的模型；先使用合成测试组织。不要把 Key 写入聊天、commit、截图或日志。
3. 在 `/app/ai/knowledge/sources` 检查知识准备状态。当前 embedding 契约固定为 `openai/text-embedding-3-small`、1536 维，索引和查询两侧必须一致。凭据解析顺序是点位 binding → 组织已验证 OpenAI 凭据 → 已配置 gateway → 安装级 OpenAI 凭据。其他聊天 provider 的 Key 不自动提供 embedding 能力。
4. 上传获准的 Wiki/文档，等待来源可用和索引完成。自定义 Agent 选择可读取的来源并保存/发布；内置 Agent 使用其组织来源策略。母文档/条目在 `/app/ai/memory` 维护。
5. 以 manager 或更高角色进入 `/app/ai/workbench`，先用“只读检查”和明确的测试对象提问。查看成功工具证据、索引版本、每项 Eval finding 和事件时间线。源链接打开本组织精确 chunk/index 的 JSON；旧版本明确标识为 historical。
6. 需要写 CRM 时再选择相应模式，核对审批卡。Mission 的“暂停客户发送/恢复客户发送”仅作用于客户发送，原因会进入既有命令审计。批准/拒绝仍通过正式服务端校验。
7. 真正客户发送还依赖可用渠道、联系人授权、发送政策、审核和发送 worker。内部同事协作另需已连接渠道与身份绑定。不要以“Run completed”宣称客户已接受报价或商业目标已完成。

## 本次验证与未验证

使用现有依赖和受控离线 fake/DB transport 测试生产函数、路由、React 组件和运行状态机；没有配置或读取 API Key，没有调用模型、embedding provider 或真实客户渠道，也没有发布部署。

最终测试命令和结果见 [离线验证记录](../testing/crm-real-runtime-parity-2026-10-01.md)：29 个 focused 文件 / 180 测试通过，完整 TypeScript 和 targeted lint 通过。新回归覆盖：共享版本记忆、初始/恢复/专家入口、当前会话 checkpoint 边界、索引/片段身份、来源撤权、builtin draft 来源读取、互补片段不误报冲突、精确来源定位、材料读取失败拒绝 Eval、重复暂停点击/不确定响应重试、已结束 Mission、可见 Eval 理由和历史 Run 界面。

没有运行完整根测试套件（其中已有 live-provider 路径）；没有运行需要真实 Supabase 的浏览器 E2E、生产数据库恢复故障注入或真实 API Key 联调。离线通过不证明某个 provider 的工具调用质量、实时价格与限额、外部消息可达性、生产 SQL/RLS 集成或视觉像素布局。

## 系统连接检查

输入是可信组织范围、已发布组织记忆、当前会话边界、成功工具观察和操作员明确命令。输出进入 Pi 上下文、已有 run events、审批队列、评测与 Workbench 详情。错误展示给操作员，恢复重新核对来源/状态；知识过期需要重查。配置入口沿用凭据、知识来源、组织记忆和 Workbench，不新增隐藏开关。只读来源投影无自主后续动作；其作用是让人能修正材料、检查事实或拒绝提案。
