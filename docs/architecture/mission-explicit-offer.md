# 明确报价与交期确认协议（评审分支）

给定负责人审定的项目、金额、币种和交期，客户需要对**这一版**报价作出明确动作；Agent 的价值是借助 CRM 工具提出发送与后续跟进，而不是自行宣布客户已接受。可观察结果是：原样报价经负责人审批并有发送账本，随后同一 WhatsApp 客户会话回传完整且唯一的确认语句。

## 执行边界

1. 负责人在商机任务旁选择该商机联系人的一对一 WhatsApp 会话，输入结构化条款。`POST /api/v1/ai/missions/:id/explicit-offer` 在任务行锁内重新核对组织、经理身份、任务未结束、发送未暂停、联系人与会话归属，按幂等键固定一版报价。金额只支持两位小数的 BRL/CNY/USD/EUR；交期是无时区的 `YYYY-MM-DD` 日期，由 SQL 格式化输出，不允许 JavaScript 时区改变日期。新版本会取代旧版本。
2. 服务返回确定性生成的完整报价正文和 128 位随机关联码。关联码不是身份凭据，而是把客户的明确回复绑定到特定报价版本；它随报价正文交付客户，因此只能与真实渠道来源一起构成证据。Agent 可以提出发送，但必须通过现有 `send_message` 草稿、负责人逐字审批、Guardrails 和发送队列。创建报价本身**不发送、不批准**消息。
3. `GET /api/v1/ai/missions/:id/explicit-offer` 在一个只读、可重复读快照中核对：同组织、同 Mission root Run 的已执行 `send_message` 提案；草稿审批正文和 CRM 出站正文都与固定报价逐字相同；发送账本的正文哈希、消息 ID、联系人、会话、幂等键、状态与审批时间一致。重复发送同一报价或身份/哈希冲突不能给出成功结论。
4. 只有该出站消息之后、到期之前，来自同组织、同联系人、同会话、同渠道 session、具有唯一外部消息 ID 的客户入站文本，去除首尾空格后**整条**等于指定确认语句，且能关联到同组织、同渠道 session、同外部消息 ID 的**已验签 WAHA 回调实际新增的同一 CRM 消息 ID**，才返回 `structuredTermsAccepted: true`，并给出出站和入站 CRM 消息 ID。回调在消息写入成功时绑定该 ID；重放时碰到已有外部 ID 不会替旧的未签名消息补证明。已编辑或撤回的回复不计入。回复“收到”“同意但交期另议”、引用确认码的否定句、无渠道消息 ID、其他会话或过期回复均不通过。完整回复存在但缺少可绑定的验签回调时标为 `unverified`。方向修订、客户变更、任务取消或新报价取代旧版时，旧版失效。
5. Agent 最终文本、商机赢单字段、普通后续回复和 LLM Judge 结论均不参与这个确定性判断。`businessOutcomeVerified` 仍是 `false`：此协议只证明 CRM 信任的渠道记录中有针对这版结构化报价/交期的明确回应，不证明自然人法律身份、合同成立、付款、其他自由文本条款或渠道提供商自身未被攻破。负责人仍需审查最终业务结论。

## 剩余验证

本地 PostgreSQL 安装/升级不变量覆盖了幂等固定、跨组织与错误会话、审批/账本/正文匹配、含糊回复、缺少 `external_id`、未验签与跨组织回调、已签名但未绑定消息的回调、撤回回复、明确回复和方向修订失效。WAHA Core 在现有默认部署中可不签名，故其客户回复**不能**让此协议给出已核验结论；部署者须接入能签名的 WAHA 版本或可信签名代理，并启用 `WAHA_WEBHOOK_REQUIRE_SIGNATURE=true`。已验签日志保留外部 ID、组织、渠道 session、CRM 消息 ID 与验签结果，原始正文按项目的数据留存规则清理；若日志证据丢失则结论回落为待核验。尚无真实 WhatsApp 客户执行这条协议的端到端记录；渠道真实送达语义与客户身份等级需要联调，不能用合成消息宣称实际客户已接受。
