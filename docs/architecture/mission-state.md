# Mission 与 Run 的边界（2026-09）

`ai_workbench_runs` 记录一次 Pi 执行；`ai_missions` 记录商机的持续业务目标。一次 Run 的 `completed` 只表示模型结束并保存了结果，Mission 会进入 `needs_review`，不能据此宣布客户已经接受报价、完成付款或达成其他业务条件。只有负责人依据 CRM/客户事实明确验收后，Mission 才会变为 `completed`。

## 已落地路径

1. 工作台以商机为范围创建 Mission，保存目标、验收条件、截止时间以及首个 Run；同一商机只允许一个未终结的 Mission。
2. Run 的数据库触发器同步 `queued`、`running`、`waiting_approval`，而 Run 结束后进入 `needs_review`。人工决定可完成、取消或转为等待客户/内部同事。
3. 客户的新文本消息进入常规 dispatch 时，先做 anti-backlog、组织/消息归属和会话资格检查，再尝试认领等待客户的 Mission。Run、唤醒标记、首事件和任务队列在一笔事务中提交。认领成功后不再触发普通渠道 Agent，避免双重回复。
4. 相同客户消息不能重复唤醒；同一联系人关联两个待续商机时不猜测归属，转人工复核。Mission 达到最大 Run 数、Agent 不可用或截止时间过期，也转人工复核。
5. 等待状态的截止时间由 worker 周期扫描；过期不是成功，也不再自动唤醒。
6. 人工完成或取消的说明与操作者保存在 Mission 上；数据库把状态迁移写入独立的 append-only `ai_mission_events`，只存对象 ID 和状态，不复制客户内容。`GET /api/v1/ai/missions/:id/events?after=<id>` 可分页回放。
7. `GET /api/v1/ai/missions/:id/evaluation` 汇总关联 Run 与 specialist、CRM 变化事件、提案、回复草稿及当前商机状态，检查部分失败、审批证据和多次客户触达风险。CRM 变更事件只有匹配已执行提案、提案预览、成功工具事件及当前 Mission 的商机 ID 才计数；目标或提案冲突会失败，缺少凭证则待复核。这仍是 Harness 执行证据，不是对商机最终字段值的独立核验。已批准发送与真正有发送回执的交付分开计数：`sent` 草稿必须能在同组织的发送账本及 CRM 消息中核对到同一任务、消息、联系人、会话、幂等键和审批正文哈希，且发送时间不早于审批时间。正文只在数据库内计算哈希比较，不进入评测 API。缺失凭证标为未核实，身份、内容或时间矛盾标为证据冲突；其它发送工具尚未接入这条回执链，不计为已触达。对已核实发送，评测另从组织内 CRM 消息读取相同联系人和会话、发送时间之后的首条入站文本消息 ID 与时间；无回复和查询证据缺失分开显示，身份或时间冲突标为失败。不会将客户消息正文放入评测 API。渠道接受发送不等于客户收到；客户后来回复也不等于客户接受报价或交期。自由文本验收条件无法由这套确定性检查自动证明，因此返回的 `businessOutcomeVerified` 始终为 `false`；人工结论明确标为 `human_attested`，不能冒充独立核验。
   补充：同一入站可能在多次发送后出现，`customerRepliesObserved` 计数的是“观察到后续入站的发送提案数”，不是独立客户回复条数；时间先后也不能证明这条入站针对该消息。缺少响应查询证据会进入待复核。
   新任务可选保存 `acceptance_contract` 版本 1：商机当前状态（进行中／赢单／丢单）与“已核实发送后同会话出现入站文本”。评测从当前 CRM 状态及独立发送／入站凭证逐项给出满足、未满足、无法核实；老任务没有契约时不伪造条件。完成中的任务若条件未满足或无法核实，结果仍需复核。即便全部满足，也只说明这些可观察信号成立，不能证明自由文本里的客户承诺、价格或交期。统一评测另从组织内的结构化报价凭证读取 `structuredOffer`：只有已审批原样发送和有可信渠道签名、绑定确切 CRM 入站消息的完整确认码才标记 `verified`；同文但无签名是 `unverified`，证据矛盾是 `conflict`。评测 API 不返回报价原文或确认码，界面只提示条款确认与完整业务验收的区别。任何结构化条款确认都不会使 `businessOutcomeVerified` 变为 `true`。
8. 工作台 Run 的结构化模型陈述独立存入 `result_document`（见 `workbench-structured-result.md`）；它可以指出缺失材料和建议唤醒条件，但不直接改变 Mission 验收、执行事实或发送权限。
9. Mission 有跨 Run 的 token 和成本上限；首轮模型调用、专职智能体调用及客户回复续跑共用同一额度。模型调用前读取已经持久化的用量，本次 Pi 循环在到达剩余额度后停止；成本未知或额度耗尽时不再自动续跑，Run 转部分完成，Mission 转人工复核。新 Mission 默认给最多四次 Run，但累计额度约为 Agent 单次预算的两倍。
10. 负责人可从商机旁将待复核任务转为 `waiting_internal`，同事提供信息后由负责人在 CRM 中提交补充。`POST /api/v1/ai/missions/:id/internal-response` 只接受负责人权限和幂等请求 ID；任务行锁内核对状态、截止时间、累计预算、Agent 版本及 CRM 范围，再一次性提交续跑 Run、输入摘要、首事件和队列任务。原文仅在新 Run 的任务中供 Agent 核查，事件和幂等账本不复制原文。补充事实不等于任何外部动作批准；发送仍须原有提案确认与最终发送闸门。
11. 负责人可从商机旁在排队、运行、等待审批或等待回复时停止 Mission。`fn_cancel_ai_mission` 在同一数据库事务中停止关联 root/专职智能体 Run、取消待审提案并失效待审草稿，同时写入 Mission 与 Run 终止事件；工作进程的租约检查拒绝已停止 Mission 的后续 CRM 写入。已批准但尚在发送队列的消息由 `fn_reply_context_current` 在最终发送策略中再次检查 Mission 状态，不能沿用过期批准。渠道已经接受的消息无法撤回，发送回执仍走原有幂等对账链路。
    客户回复审批与 Agent 续跑之间还存在单独的进程中断点：`fn_reply_action` 在同一数据库事务中认领等待确认的 Run，并保存草稿、提案及发送 job；HTTP 在调用前退出不会使 Run 卡在 `running`。随后服务端把决策观察写入私有 Pi 消息并入队续跑。`ai_workbench_send_decision_receipts` 以提案 ID 幂等记录后一阶段，观察、产品事件、续跑 job 和收据同事务提交。HTTP 若在两个事务间退出，Worker 启动及 reaper 会从已保存的草稿／提案恢复，绝不再次执行发送。私有 Pi 状态缺失时 Run 转为 `partial`，不伪造上下文或重复发送。批准只表示发送已排队，仍不等于客户收到。非发送提案的人工拒绝没有外部工具副作用：提案拒绝、私有 Pi 观察、脱敏产品事件与续跑 job 现在在一笔事务中提交；队列写入失败会回滚拒绝本身。若还有其他待审提案，则 Run 保持等待，不提前续跑。其余非发送工具的**批准**先持久化 `approved` 执行意图，再调用工具；已知结果、Pi 观察和续跑 job 同事务提交。执行后进程中断或工具结果不确定时，不自动重放，Worker 将逾期意图标为需对账并使 Run 部分完成。这保证不会假装成功，却不等于外部副作用的 exactly-once：需要业务端幂等键和独立回执才能自动确认或恢复。
12. 持续任务在首轮创建、客户消息唤醒、内部补充续跑及 Worker 副作用前，统一核对 Agent 是否仍自动运行、未暂停、未归档、未停用，并绑定原 Run 的精确版本。普通 Agent 需要该版本仍已发布；锁定内置 Agent 使用组织默认模型绑定下的草稿版本，不误用 `published_version_id`。PostgreSQL 的 `bigint` 运行修订号会安全转换为 JavaScript 整数，无法表示时拒绝续跑。最终客户发送闸门也会对 Mission 核对 Agent 的启用/暂停/自动状态；模型提交的唤醒条件仍只是建议，不能绕过这些规则。
13. 飞书内部文本回复已有独立事件入口（见 `internal-collaboration-feishu.md`）：验签、解密和过期检查后，按已核验的租户、员工和回复线程映射到一个 Mission；加密 inbox 与队列 job 原子提交后即应答。Worker 解密并在创建续跑 Run 的事务中再次验证映射及员工角色，同一飞书事件只能生成一个 Run。负责人可从商机侧授权问题，也可在关联 Mission 的 CRM 主管 Agent 提案中核对收件人和原文后批准。后者不是模型直发：批准事务将提案、加密 outbox、队列、当前 Run 终态和 Mission 等待状态一起提交。发送成功后用真实消息 ID 建立回复线程映射，再沿上述入站路径继续。提供事实的同事不会因此成为 Agent 的执行身份，Run 仍使用原任务负责人的身份；飞书文本不是审批。
14. 负责人可在商机侧用幂等命令暂停或恢复此 Mission 的客户发送。`ai_mission_commands` 以独立 append-only 记录操作者、原因、命令与发送策略修订；命令和策略位在同一事务提交。暂停撤销尚未进入 `sending` 的已批准草稿及其队列任务；审批前与渠道发送前都重新读取暂停位。最近暂停时间持续使旧批准失效，快速恢复也不会让旧批准自动重发。待审草稿可在恢复后重新人工审批；已进入传输的消息不能保证撤回，仍需按原发送账本对账。
15. 在 `queued`、`running`、`needs_review`、`waiting_customer` 或 `waiting_approval` 时，负责人可用 `POST /api/v1/ai/missions/:id/follow-up` 补充方向。事务先通过发送策略命令暂停旧客户发送，再检查组织身份、任务状态、期限、累计预算、Agent 精确版本和 CRM 范围；成功时更新 Mission 当前方向及修订、创建新 Run、写入幂等摘要／首事件并入队。排队／运行中的旧 root 和活跃只读 specialist 会在同一事务取消，旧待审草稿及提案撤销，旧 Run 和子 Run 写入取消事件；数据库在 specialist 创建、重领及提案插入时锁定旧 root，取消后不能重新启动旧子任务或提出旧动作。待审批状态同样锁定并取消旧 Run，但必须能找到旧待审提案；若审批已抢占旧 Run，请求失败并回滚。新方向是任务记忆，后续客户回复或同事资料唤醒也会带入，但每次都必须重新读取 CRM 事实；已经完成的业务动作不会自动回滚。方向原文只在经理可见的 Mission 与 Run 任务里，事件和账本不复制。重放相同请求不会重新暂停或生成第二个 Run；若负责人之后单独恢复了发送权限，重放会返回当前策略状态。这是受控取消并新建 Run，不是 Pi 原地 steer，也不是报价或外发批准。
   方向的“已接受”与“已消费”分开记录：提交时只增加 `direction_revision`；Worker 在模型调用时传入私有方向探针，Pi 适配层在 `transformContext` 之后的最终模型上下文转换点核对 user 消息，并仅在对应回合非错误结束后发出不含原文的 `model_context_consumed`。Worker 再核对保存的 transcript、Run 修订与探针 ID，在同一事务写入私有消息状态、`direction_consumed_revision`、输入账本消费时间与不含原文的 `manager_direction_consumed` 事件。页面轮询显示“等待模型消费”或“模型已读取”，两者都不等于业务完成。

## 尚未形成完整闭环

- `waiting_internal` 已支持 CRM 负责人录入、负责人授权飞书提问、CRM 主管 Agent 的待审提问，以及已绑定线程的回复续跑，但缺少飞书应用安装/身份绑定流程、审批卡片和真实租户联调；企业微信尚未接入。它不是可直接交付使用的内部渠道闭环。
- Mission 已能逐项核对用户显式选择的两类可观察条件。经理可以显式触发有成本的客户答复语义审查：只把已核实发送后、同组织/联系人/会话的客户入站文本给独立 Judge，要求每条引用逐字对应原始消息；材料超限时拒绝截断后给结论。此结果独立于执行 Agent 的自述，但仍是模型解释，不是客户身份、合同成立或自由文本承诺的确定性证明，`businessOutcomeVerified` 继续为 `false`。[结构化报价与交期的明确确认协议](mission-explicit-offer.md)已进入统一 Mission 评测：只有原样审批发送和有签名归属的完整确认码均能核对，才报告这版条款有明确渠道回复。它尚未通过真实客户渠道联调，也不覆盖其他自由文本条款或法律身份。不能把商机状态“赢单”或普通后续入站直接当作报价接受。
- 累计预算依据 `llm_calls` 中已经持久化的调用统计。Mission 的 specialist 顺序运行，避免兄弟调用同时读取旧余额；普通独立审查仍可并发。一次模型请求自身可能越过剩余额度，所以它仍是“调用前检查 + 每轮停止”，不是 provider 级原子预扣；完全硬性的上限需要预留额度/结算机制。
- 客户唤醒目前仅支持文本；音频等媒体仍由原渠道链路处理。
- Mission 事件覆盖状态迁移；内部补充已有幂等账本及 Run 首事件的 ID 引用，但尚未与客户触达结果、人工确认理由组成完整的业务证据图。Run 事件仍是工具执行过程的审计来源。
- 人工批准 `crm_update_lead` 不能把“可撤销写入”降级为普通更新：与自动执行相同，必须先读到当前值、限定可恢复字段并生成业务补偿参数；无法生成时不调用写入工具。这个约束不等于跨进程原子回滚：工具已经写入、提案结果尚未保存时进程退出，仍需依据 CRM 现状人工对账。
- “停止”与已经进入外部传输的消息存在不可逆边界：策略会在真正调用渠道前再检查一次，但如果渠道已接受，系统只能对账，不能承诺撤回。界面明确提示这一点。
- 负责人现在可在排队／运行中受控取消旧 Run 并启动新 Run，且新 Run 的方向有模型上下文消费回执；但尚未实现同一 Pi turn 内的可信负责人 `steer` 注入及其跨崩溃回放，或员工从飞书下达控制命令。旧模型请求可能已经在途，其结果不再取得旧 Run 的 CRM 执行权；已完成的 CRM 动作仍需新 Run 核对。暂停直接作用于发送策略，不依赖模型理解文字。最终策略检查与外部网络调用之间仍有不可消除的在途竞态；暂停确认不能承诺召回已越过发送切点的请求。

上线前需要按上述缺口补齐内部消息端口、业务结果评测和累计预算，并用真实渠道完成端到端验收。不要把合成数据的通过结果称作真实客户闭环。
