# CRM 知识与客户承诺的最小示例

这是纯文档的虚构设计样例。公司、客户、价格、消息、审批人、记录 ID 和日期均为演示数据，不是本 CRM 的真实商业规则，也不是已接入系统的测试租户。

这个例子回答销售的一个实际问题：客户要求降价并提前交付，助手怎样找到适用规则、识别没被确认的承诺，并给出能审阅的回复？

## 从这五页开始

1. [原始来源与版本登记](sources.md)：每条事实从哪里来，什么已经过期，谁有权批准
2. [产品与报价](product-and-pricing.md)：当前报价、适用范围、折扣边界
3. [交期与异议回答](delivery-and-objections.md)：哪些能答，哪些必须问交付负责人
4. [星桥商贸的客户承诺](customer-commitments.md)：客户的愿望与我方承诺分别保存
5. [检索、回复与验收](retrieval-and-evaluation.md)：从一个问题走到有依据的草稿，以及必须拒绝的错误答案

相关架构建议见[销售与 Agent 审阅](../crm-sales-agent-review-2026-10-01.md)。

## 示例的范围

- 前两类公司知识可作为将来组织 Wiki 的内容示范；客户承诺页只示范按客户范围的派生视图，不能直接混入全公司可读的知识库。
- 文中的状态、有效期和访问范围是建议的产品契约。当前应用不会因为 Markdown 写了这些字就执行 ACL、过期过滤或自动更新。
- 链接指向本目录真实存在的样例文档与原始材料片段，不伪造实际 CRM 页面、客户消息链接或运行 UUID。
- 没有导入数据库、调用嵌入模型、配置第三方或注册任何新工具。

## 这为什么称得上 Wiki 示例

同一批准价格来源被产品页、异议页和销售回复共同引用；客户页只链接适用政策，不复制一份独立价格。来源更新时能沿反向引用找到受影响页面与草稿。每一条商业陈述都能返回到原文，而不是只相信一段模型总结。

真正落地还需要：结构化来源登记、发布与撤权、稳定版本定位、按角色与客户范围检索、变更影响分析、待审修订、内容删除传播和回归测试。这些不在本示例中实现。
